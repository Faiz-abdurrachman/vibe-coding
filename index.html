Mindset Shift: Blind Prompting vs Spec-Driven Vibe Coding

AI tanpa kendali menghasilkan kode rentan. Insinyur sejati memagari AI dengan Triad Dokumen Pengendali.

ANTI-PATTERN: BLIND PROMPTING Pola Amatir
// Prompt sembarang tanpa pagar:
"Tolong bikinin aplikasi kas kelas yang keren dong, bebas pakai apa aja..."
Halusinasi Fitur: Tombol Edit/Hapus hilang karena tidak tertulis jelas.
Celah XSS Terbuka: AI secara otomatis memakai .innerHTML yang mudah disuntik script hacker.
Test Case Gagal: Nominal negatif diterima begitu saja tanpa validasi TC-01.
Hasil: Aplikasi rapuh, tidak lolos pengujian SKPL, dan rawan eksploitasi.
PRODUCTION STANDARD: SPEC-DRIVEN Standard Industri
// Kendalikan AI dengan Triad Dokumen:
"Implementasikan fungsi CRUD mengacu pada @PRD.md dan terapkan aturan ketat di @RULES.md"

100% Deterministic: AI patuh pada nama kolom, constraint, dan flow panitia.
Zero Security Vulnerabilities: Bebas celah XSS dan aman dari kebocoran key.

LANGKAH 3 • MENIT 35–45 • PAGAR KEAMANAN SIBER

Pasang Pagar Pengaman RULES.md di VS Code

Khusus mahasiswa RKS & TI: Kita melarang AI memakai pola rentan sebelum menulis satu baris kode JavaScript pun.

PILAR 1: ANTI-XSS DOM POLICY MUTLAK
Dilarang Keras: Merender kolom keterangan dari user menggunakan .innerHTML.
Wajib: Gunakan .textContent atau sanitasi ketat escapeHtml() agar tag script tidak pernah dieksekusi browser.
element.textContent = data.keterangan; // 100% AMAN DARI XSS
PILAR 2: VALIDASI INPUT (TC-01) CLIENT-SIDE
Sebelum mengirim payload ke Supabase, periksa nominal > 0.
Jika user menginput angka minus/nol (contoh: -50000), batalkan simpan dan tampilkan banner alert persis: "Nominal harus lebih dari 0".
if (nominal <= 0) return showAlert("Nominal harus lebih dari 0");
PILAR 3: ISOLASI KREDENSIAL AUTH SAFETY
Hanya gunakan SUPABASE_ANON_KEY (Public Key) di frontend.
Dilarang Keras: Menaruh service_role_key atau STITCH_API_KEY di dalam file index.html publik.
const supabase = createClient(SUPABASE_URL, SUPABASE_ANON_KEY);
PILAR 4: PROTEKSI .GITIGNORE REPO LEAK PROOF
Sebelum push ke GitHub, pastikan file .gitignore mengecualikan berkas sensitif: .env, .vscode/mcp.json, dan token pribadi.
.env* • .vscode/mcp.json • .cursor/mcp.json
LANGKAH 4 • MENIT 45–75 • DATABASE CLOUD & WIRING

Supabase Cloud DB & Defense in Depth

Validasi ganda: Mengunci aturan TC-01 langsung di level database PostgreSQL via CHECK constraint.

SQL Editor Supabase (Salin & Jalankan) 
-- 1. Buat Tabel cash_transactions sesuai Modul 2 SKPL
CREATE TABLE IF NOT EXISTS public.cash_transactions (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tanggal DATE NOT NULL DEFAULT CURRENT_DATE,
    jenis_transaksi TEXT NOT NULL CHECK (jenis_transaksi IN ('Masuk', 'Keluar')),
    nominal NUMERIC(12, 2) NOT NULL CHECK (nominal > 0), -- Kunci TC-01 di Database!
    keterangan TEXT NOT NULL CHECK (char_length(trim(keterangan)) > 0),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 2. Aktifkan Row Level Security (RLS)
ALTER TABLE public.cash_transactions ENABLE ROW LEVEL SECURITY;

-- 3. Kebijakan CRUD Publik untuk Key Anon (Workshop)
CREATE POLICY "Akses publik CRUD kas kelas"
ON public.cash_transactions FOR ALL TO anon
USING (true) WITH CHECK (nominal > 0);
Check Constraint (nominal > 0) memastikan hacker tidak bisa bypass via curl/Postman.
Arsitektur Pertahanan Berlapis (Defense in Depth)
L1
Validasi Frontend (JavaScript)
Mencegah angka minus sebelum tombol kirim ditekan (Respons instan untuk user).
L2
API Gateway & Row Level Security
Memvalidasi izin operasi anon key dan memblokir modifikasi tidak sah.
L3
Database Engine Check Constraint
Jika hacker menembak API langsung, PostgreSQL tetap membatalkan transaksi.
Konsep ini menjadi nilai plus besar saat mahasiswa mempresentasikan portofolio!
